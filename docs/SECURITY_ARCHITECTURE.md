# SurakshaOS — Security Architecture

**Status:** PLANNED — not yet implemented  
**Current milestone:** M4 (Secure OS)

---

## Design Philosophy

SurakshaOS is security-first. Every design decision considers security implications. The security architecture is built on:

1. **Defense in depth** — multiple independent security layers
2. **Least privilege** — processes only access what they need
3. **No ambient authority** — every resource access requires explicit authorization
4. **Security by code, not by comments** — enforcement via architecture, not documentation
5. **Transparency** — all security mechanisms are auditable

## Capability System

### Design

Every resource access requires a capability token:

```
Capability {
    id: u64,           // Unique, unforgeable token ID
    resource: Resource, // What resource this grants access to
    permissions: Flags, // READ, WRITE, EXECUTE, etc.
    ttl: Option<u64>,   // Time-to-live (optional expiration)
    owner: ProcessId,   // Which process owns this capability
}
```

### Enforcement

- Capabilities are checked on every syscall that accesses a resource
- Capabilities cannot be forged (generated by kernel only)
- Capabilities can be delegated (with restrictions)
- Capabilities can be revoked by the owner or system
- Expired capabilities are automatically invalid

### Resource Types

- Files and directories
- Network sockets
- Devices
- IPC channels
- Memory regions
- System operations (reboot, mount, etc.)

## Process Isolation

### Virtual Memory Isolation

- Each process has its own virtual address space
- Kernel pages are not mapped in user space (or mapped read-only)
- Page table isolation prevents cross-process memory access
- W^X enforced: pages cannot be both writable and executable

### Process Credentials

```
ProcessCredentials {
    uid: u32,           // User ID
    gid: u32,           // Group ID
    capabilities: CapSet, // Active capabilities
    sandbox: SandboxConfig, // Sandbox restrictions
}
```

### Privilege Levels

- **U-mode (User):** Applications run here. No direct hardware access.
- **S-mode (Supervisor):** Kernel runs here. Manages processes and resources.
- **M-mode (Machine):** Firmware/bootloader only. Not used after boot.

## Sandboxing

### Sandbox Configuration

```
SandboxConfig {
    filesystem: FsPolicy,      // Allowed paths, read/write
    network: NetworkPolicy,     // Allowed connections, ports
    devices: DevicePolicy,      // Allowed devices
    ipc: IpcPolicy,            // Allowed IPC endpoints
    memory: MemoryPolicy,      // Memory limits
    cpu: CpuPolicy,            // CPU time limits
}
```

### Filesystem Sandbox

- Per-app allowed path list
- Read-only vs read-write vs no-access
- Temporary storage isolated per app
- No access to kernel/other-app storage

### Network Sandbox

- Per-app network permission
- Allowed ports and protocols
- DNS filtering
- Connection limits

### Device Sandbox

- Explicit device access list
- Camera, microphone, location each require separate permission
- Sensor access controlled individually

## Cryptography

### Guiding Principle

> Do NOT invent cryptography. Use well-reviewed implementations.

### Planned Algorithms

| Purpose | Algorithm | Standard |
|---------|-----------|----------|
| Hashing | SHA-256 | FIPS 180-4 |
| Key exchange | ML-KEM-768 | NIST FIPS 203 |
| Digital signatures | ML-DSA-65 | NIST FIPS 204 |
| Symmetric encryption | AES-256-GCM | NIST SP 800-38D |
| Secure random | Hardware RNG + DRBG | NIST SP 800-90A |
| Key derivation | HKDF | RFC 5869 |

### Cryptographic API

```rust
// Hashing
fn sha256(data: &[u8]) -> [u8; 32];

// Signatures
fn sign(sk: &SigningKey, msg: &[u8]) -> Signature;
fn verify(pk: &VerifyingKey, msg: &[u8], sig: &Signature) -> bool;

// Encryption
fn encrypt(key: &Key, nonce: &[u8], plaintext: &[u8]) -> Vec<u8>;
fn decrypt(key: &Key, nonce: &[u8], ciphertext: &[u8]) -> Result<Vec<u8>>;

// Key exchange
fn kem_encapsulate(pk: &PublicKey) -> (Ciphertext, SharedSecret);
fn kem_decapsulate(sk: &SecretKey, ct: &Ciphertext) -> SharedSecret;

// Random
fn secure_random(buf: &mut [u8]);
```

### Key Storage

- Hardware-backed key storage where available
- Kernel-protected key store
- Per-process key isolation
- No keys in userspace memory (where possible)

## Secure Boot

### Boot Chain

```
Boot ROM (hardware)
    │
    ├── Verifies bootloader signature
    │
Bootloader (verified)
    │
    ├── Verifies kernel signature
    │
Kernel (verified)
    │
    ├── Verifies system services
    │
System Services (verified)
    │
    ├── Verifies application signatures
    │
Applications (verified)
```

### Verification

- Each stage verifies the next using public keys
- Keys stored in hardware (where available) or in protected storage
- Rollback protection: version anti-rollback counters
- Failed verification → halt (no fallback to unverified code)

## Signed Packages

### Package Format

```
Package {
    manifest: Manifest,    // Name, version, dependencies
    payload: Vec<u8>,      // Compressed application data
    signature: Signature,  // Developer's signature
    hash: [u8; 32],        // SHA-256 of payload
}
```

### Verification

1. Verify signature against known developer public key
2. Verify hash matches payload
3. Verify dependencies are also signed
4. Verify package is not revoked
5. Install only if all checks pass

## Entropy / Randomness

### Sources

1. Hardware RNG (RISC-V `rdrand` or platform-specific)
2. Timing jitter (if hardware RNG unavailable)
3. Device-specific entropy (interrupt timing, etc.)

### Architecture

```
Hardware RNG → Entropy Pool → DRBG → Cryptographic Random
                  ↑
         Timing Jitter (backup)
```

- Entropy pool collects from multiple sources
- DRBG (Deterministic Random Bit Generator) provides cryptographic randomness
- Reseeded periodically with fresh entropy
- Prediction resistance enabled

## Audit Logging

### Events Logged

- Process creation/destruction
- Capability grant/revoke
- File access (optional, performance impact)
- Network connections (optional)
- Security policy violations
- Authentication events
- System configuration changes

### Log Format

```
[TIMESTAMP] [LEVEL] [PROCESS] [EVENT] [DETAILS]
```

### Log Protection

- Logs are append-only
- Logs cannot be deleted by user processes
- Logs are signed to prevent tampering
- Log storage is size-limited with rotation
